# Java Webapp Migration Questions Validation

Date: 2026-07-20

Question: does a deterministic, evidence-backed output layer for the seven Kubernetes P0 migration questions generalize across roughly 10 GitHub Java web application repositories similar enough to `mybatis/jpetstore-6`?

Scope: primary repository sources only: README, Dockerfile, Docker Compose, Maven/Gradle build files, `application*.yml` / `application*.properties`, `web.xml`, SQL/init files, and Kubernetes manifests when present. Missing standard files are recorded as coverage gaps, not as repository failures.

## Proposed Seven-Question Layer

The existing model can be validated as a thin report layer over deterministic facts:

1. What components exist?
2. Which Kubernetes workload should each component map to?
3. Which ports and Services are needed?
4. What must persist?
5. Which ConfigMap and Secret inputs are needed?
6. What must run first at startup or initialization?
7. What remains undecidable from repository facts?

For each answer, the proposed model fields should be preserved:

| Field | Validation rule |
| --- | --- |
| `status` | `complete`, `partial`, or `unresolved`; this is a coverage/result label, not confidence inflation. |
| `basis/evidence` | Direct links to primary source files and file classes that support the answer. |
| `missing/unresolved` | Missing standard files and operational inputs the repository cannot decide. |

## Candidate Selection Criteria

Selected repositories meet most of these criteria:

- Public GitHub repository with a Java web application or deployable Java web backend.
- Maven or Gradle build metadata is present.
- At least one HTTP-serving application signal is present: Spring Boot web dependency, servlet/WAR packaging, README run URL, Compose port, Dockerfile `EXPOSE`, or `web.xml`.
- At least one migration-relevant source class is present beyond the README: Dockerfile, Compose, app config, SQL/init, `web.xml`, or Kubernetes manifests.
- Stack shape is similar enough to JPetStore for general rules to matter: Spring Boot web app, servlet/WAR app, MyBatis/MyBatis-plus, database-backed web application, or multi-service Java web system.
- Repositories are intentionally varied so the layer is not overfit to JPetStore: single WAR, Spring Boot executable JAR, multi-module Maven, Gradle, Compose-backed infrastructure, generated Docker/Jib/buildpack paths, and missing-file cases.

## Generalization Findings

The seven-question layer generalizes if each answer is treated as an evidence-backed coverage result, not as a manifest generator.

`components` generalizes well from Maven/Gradle modules, README run commands, Docker/Compose services, WAR packaging, Spring Boot plugins, and web modules. Multi-module repositories require module selection rules based on deployability signals: Spring Boot plugin, executable JAR/WAR packaging, Compose build context, README run module, or Dockerfile context.

`workload mapping` is usually derivable at P0 as a candidate: stateless HTTP app to Deployment + Service, DB/cache/search/object-storage services to StatefulSet or external managed service, one-shot migration tools to Job, frontend Nginx to Deployment + Service. The candidate must be labelled `derived`; StatefulSet vs managed service and exact controller details remain operational decisions unless manifests already exist.

`ports/services` generalizes from Compose `ports`, Dockerfile `EXPOSE`, README URLs, Spring Boot `server.port`, servlet-container defaults only when explicitly supported by repo facts, and K8s manifests if present. Missing ports should be a coverage gap, not a failure.

`persistence` generalizes from SQL/init directories, embedded database config, datasource URLs, Compose volumes, Docker run `-v`, and database service images. The app PVC must not be inferred merely because the app uses a database; persistent database state and application-local filesystem state are separate facts.

`ConfigMap/Secret` generalizes from `application*.yml/properties`, Compose environment variables, Dockerfile `ARG`/`ENV`, and documented run environment variables. Secret classification should be content-pattern based (`password`, `secret`, `token`, credentials) and evidence-backed; hard-coded sample values remain sample values, not production defaults.

`startup/init` generalizes from Compose `depends_on`, SQL init scripts, Flyway/Liquibase dependencies, Spring SQL init properties, startup shell scripts, and README commands. The layer should distinguish in-process startup init from one-shot migration Jobs.

`unresolved` is the strongest generalizable field. Across the sample, repositories consistently do not decide replica count, CPU/memory, Service type, IngressClass, HPA, PDB, StorageClass, DB HA/backup, production database endpoint, production Secret values, and often health probes. Recording these as unresolved is a feature, not a weakness.

## Concrete Adjustments

Proceed with the seven-question output layer, with these adjustments to avoid repository-specific rules:

1. Use file-class discovery and content parsing only. Never key logic on repository names such as `jpetstore`, `petclinic`, `jhipster`, or `mall`.
2. Add a source coverage matrix to the output: README, build file, app config, Dockerfile, Compose, `web.xml`, SQL/init, K8s. Mark missing classes as `coverage_gap`.
3. Model per-question status independently. A repo can be `complete` for ports but `partial` for persistence or health.
4. Treat documentation-path Compose files (`docs/`, `document/`, `examples/`) as evidence with a `sample_or_documented_deployment` status unless README/build context selects them as the deployment topology.
5. Add deployable-module selection rules for multi-module Maven/Gradle: Spring Boot plugin, WAR packaging, executable application class, Compose build context, Dockerfile context, or README run command.
6. Separate `runtime_dependencies` from `workload_mappings`: MySQL/Redis/PostgreSQL in Compose can become candidate workloads, but managed-service replacement remains unresolved.
7. Separate `application_persistence` from `database_persistence`: SQL tables or datasource use do not imply an app PVC.
8. Support image-only evidence from README/Compose as `image.reference` while leaving Dockerfile internals unresolved when no Dockerfile exists.
9. Keep health probes conservative: derive from Actuator, Compose healthcheck, explicit README endpoint, or K8s manifest; otherwise emit unresolved probe input.
10. Preserve `status`, `basis/evidence`, and `missing/unresolved` in the Markdown report so partial evidence is visible rather than collapsed into yes/no answers.

## Conclusion

Decision: proceed, with adjustments.

The seven-question layer generalizes across the sampled Java web application repositories because the questions map to standard repository evidence classes rather than JPetStore-specific concepts. The model is most reliable when it reports deterministic facts and coverage gaps separately: source-backed answers where files exist, `partial` where the evidence class is absent or only sample/development-oriented, and `unresolved` for operational decisions the repository cannot own.

The key implementation risk is overreach: turning common framework defaults, README examples, or documentation-only Compose files into production conclusions. The concrete fix is to keep every answer attached to file-class evidence and to expose missing/unresolved fields prominently.
